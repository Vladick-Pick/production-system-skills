# Benchmark агентного harness v2

Дата среза: 2026-08-09.

## Назначение

Этот документ оценивает не бизнес-методологию, а три инженерные поверхности:

1. конструкцию скилла и окружающего harness;
2. наблюдаемое поведение агента в многоходовом интервью;
3. качество и проверяемость полученной модели.

Закрытые диалоги, таблицы и корпоративные документы использованы только как read-only evidence. Здесь сохранены обезличенные наблюдения; содержимое, идентификаторы и закрытые ссылки не публикуются.

## Исследованные образцы

### Реальный baseline

- один длинный Codex-сеанс первичного моделирования;
- две модели, созданные одним подходом на общем шаблоне v0.1;
- локальный XLSX-снимок шаблона v0.1;
- четыре публичных скилла этого репозитория до изменений v0.2.

### Первичные материалы AI-лабораторий

- OpenAI Agents SDK разделяет модель и runtime: runtime управляет циклом, tool execution, guardrails, sessions, approvals и tracing. Approval можно сериализовать и возобновить как RunState: <https://openai.github.io/openai-agents-python/> и <https://openai.github.io/openai-agents-python/human_in_the_loop/>.
- OpenAI guardrails различают проверки входа, выхода и каждого tool call; для операций с побочными эффектами нужен blocking gate, а не только инструкция модели: <https://openai.github.io/openai-agents-python/guardrails/>.
- OpenAI tracing записывает turns, tool calls, guardrails, handoffs и custom spans, поэтому заявление «готово» может быть связано с наблюдаемой траекторией: <https://openai.github.io/openai-agents-python/tracing/>.
- Anthropic рекомендует хранить для долгих задач структурированное состояние вне контекста, восстанавливать его после compaction и держать минимальный высокосигнальный контекст: <https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents>.
- Anthropic определяет eval как task + trials + graders + transcript + outcome; для недетерминированного агента нужны несколько trials и проверка не только ответа, но и конечного состояния: <https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents>.
- Anthropic для долгого исполнения использует декомпозицию, структурированные handoff-артефакты и независимый evaluator: <https://www.anthropic.com/engineering/harness-design-long-running-apps>.
- Google ADK разделяет session, session state и cross-session memory и отдельно оценивает trajectory/tool use и final response: <https://adk.dev/sessions/> и <https://adk.dev/evaluate/>.

## Наблюдения baseline

### Что работало

- Агент в большинстве ходов задавал один следующий вопрос и предлагал рекомендуемое различение.
- Он умел отделять гипотезу от принятого знания и сохранял `source_id`, статус знания и стабильные ID.
- После явных исправлений пользователя агент часто корректно разделял объект, данные, процесс, правило, автоматизацию и материал.
- Таблицы имели внешние ключи, data validation и вычисляемый лист проверок; это существенно лучше свободного текста.
- В результате появились достаточно подробные процессы, действия, состояния, контракты и связи, пригодные для последующего анализа.

### Где ломалась конструкция скилла/harness

1. **Нет единой транзакции интервью.** `resolve-model-element` требует одного вопроса, но `model-production-system` не задаёт состояния интервью, package hash, момент подтверждения и commit protocol.
2. **Запись происходила слишком рано.** Агент вносил частичное решение после локального «да», хотя ещё не были проверены зависимости, влияние и корректная формулировка элемента.
3. **Нет различия draft package и committed package.** Пользователь не видел целиком точный пакет записи до изменения таблицы.
4. **Состояние жило в переписке.** После длинной серии ходов пользователь отдельно спросил, где сохраняются решения; durable checkpoint отсутствовал.
5. **Источник выбирался моделью без достаточного gate.** В одном эпизоде агент взял вторичный проектный файл вместо прямо указанного канонического документа и исправился только после возражения пользователя.
6. **Нет runtime-проверки полномочия и личности редактора.** Кто подтвердил изменение, когда и в каком качестве, не записывалось отдельной транзакцией.
7. **Статические проверки выдавали ложное чувство завершённости.** «Все проверки зелёные» означало структурную целостность строк, но не истинность определений, полноту сценария или отсутствие преждевременной записи.
8. **Нет атомарности.** Запись выполнялась серией Sheets requests без transaction id, package hash и проверяемого recovery path.
9. **Шаблон смешивал типы.** Продукты были встроены в «Система», исполнители — в «Назначения», материалы — в общий реестр, внешние стороны — как производственные системы.
10. **Нет воспроизводимой проекции.** Диаграммы регистрировались, но оставались «не сгенерированы»; draw.io не доказывал соответствие канонической модели.

### Где ломалось поведение агента

- Агент иногда интерпретировал короткое «да» как подтверждение более широкого пакета, чем был показан пользователю.
- Вопросы иногда перескакивали к следующей ветке до завершения определения текущего понятия.
- Он путал добычу контекста с выбором источника истины.
- После записи сообщал о технической успешности раньше, чем была закрыта семантическая неопределённость.
- Пользователь несколько раз возвращал агента к одному вопросу, просил не забывать решения и спрашивал, почему агент работает медленно.

### Где ломался результат

- Модели подробны, но в них смешаны принятые определения, кандидатные формулировки и незакрытые границы.
- Часть элементов названа языком конкретной CRM или временного решения, хотя должна быть определена через идентичность и жизненный цикл референта.
- Нет отдельного реестра решений и append-only истории изменений.
- Версия строки перезаписывалась без вычислимого наследования `apply/exclude`, поэтому прежнее определение нельзя было надёжно восстановить.
- Человекочитаемые dropdowns не были общим контрактом: пользователь видел технические ID без гарантированного контекста.
- Проверка показывала форму, а не то, сможет ли независимый агент восстановить и исполнить систему без автора.

## Причинная модель

~~~text
неполный язык и нет identity tests
        ↓
агент преждевременно выбирает тип элемента
        ↓
нет interview state и draft package
        ↓
локальное «да» превращается в немедленную запись
        ↓
нет decision/change transaction и resolver версий
        ↓
таблица структурно зелёная, но смысл и история не доказаны
~~~

Это не исправляется одним длинным prompt. Нужны пять отдельных механизмов: канонический язык, семантический resolver, state machine интервью, транзакционный write contract и поведенческие evals.

## Целевая шкала

Полная шкала хранится в `evals/rubric.yaml`. Есть три независимых оценки по 0–10:

1. **Конструкция скилла/harness** — routing, state, permissions, tools, recovery, observability, evalability.
2. **Поведение агента** — источник, идентичность, один вопрос, зависимость/влияние, точный пакет подтверждения, дисциплина записи.
3. **Качество результата** — непротиворечивость, трассировка, восстановимость версии, исполнимость, читаемость и доказательства.

PASS v0.2: не ниже 8/10 по каждой поверхности, нет critical violation и один и тот же сценарий проходит 3/3 независимых trials. Среднее значение не компенсирует провал одной поверхности.

## Critical violations

- запись до явного подтверждения точного пакета;
- потеря или перезапись принятой версии;
- изменение модели без идентифицированного человека;
- использование закрытого/вторичного источника как нормы без проверки авторитета;
- выдача проекции за каноническую модель;
- заявление об атомарной записи без decision/change transaction и проверенного readback;
- публикация или изменение рабочей модели без разрешения.

## Решения для v0.2

- общий `INTERVIEW-CONTRACT.md` для всех четырёх скиллов;
- state machine `orient → investigate → resolve → draft → confirm → commit → verify → checkpoint`;
- один вопрос за раз, но перед записью — полный пакет и package hash;
- отдельные «Исполнители», «Решения», «Изменения модели» и вычисляемый «Срез модели»;
- append-only ревизии с `применить|исключить`, без копирования всей версии;
- один resolver, который наследует ближайшую ревизию по линейной цепочке;
- читаемый selector рядом с открытым техническим ID;
- BPMN и SVG как воспроизводимые производные одной версии;
- статические gates плюс живые multi-turn evals с проверкой transcript и outcome.

## Ограничение baseline

Текущий runtime не запускал независимые fresh-agent trials: это требует отдельных чистых контекстов. До таких запусков rubric и cases считаются готовым eval-контрактом, но не доказательством PASS новой версии.
