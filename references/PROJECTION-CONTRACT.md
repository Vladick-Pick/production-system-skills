# Контракт представлений

Реестр, схема, playbook, исполнительский регламент, обучение и спецификация интерфейса являются представлениями принятой версии технологического кита.

## 1. Манифест

Каждое представление содержит:

- ID;
- тип;
- назначение и аудиторию;
- version_id исходной модели;
- дату построения;
- включённые element_id;
- исключённые элементы и причину;
- неполное покрытие;
- статус актуальности;
- способ повторного построения.

## 2. Трассировка схемы

- действие → action_id;
- дорожка → position_id;
- состояние → state_id;
- развилка → ID условия или решения;
- ребро → edge_id;
- группа → process_id.

Схема может менять расположение, но не создавать узел без элемента модели.

## 3. Трассировка документов

- раздел playbook → position_id или process_id;
- шаг → action_id;
- правило → ID правила;
- форма или шаблон → ID материала;
- критерий → ID контракта или приёмки.

## 4. Направление изменения

~~~text
изменить модель
→ принять новую версию
→ пересобрать представление
~~~

Правка производного документа создаёт предложение к модели, а не обратную запись.

## 5. Актуальность

Представление устарело, если:

- его version_id отличается от действующей версии;
- изменён включённый элемент;
- отсутствуют исходные ID;
- изменился профиль аудитории;
- из представления выпали исключения, возвраты, полномочия или критерии приёмки.

## 6. Ответственность четырёх скиллов

- model-production-system создаёт проекционно готовые ID и связи;
- maintain-production-system пересобирает затронутые представления после принятого изменения;
- audit-production-system сравнивает представления с принятой версией;
- resolve-model-element не распространяет определение в представления до отдельного подтверждения границы влияния.
