# Миграция рабочей книги v0.3 → v0.4

Этот runbook исполняет `maintain-production-system`. Он переводит отдельную копию точной книги v0.3 в физический контракт v0.4, сохраняя существующую модель и запрашивая только новый смысл, который нельзя доказать из источника. Исходная v0.3 не изменяется.

## Результат

- отдельная книга v0.4 из 37 листов;
- сохранённые stable IDs, версии, решения, история и все незатронутые авторские значения;
- разрешённые legacy-показатели в `Показатели` и legacy-нормативы в `Требования показателей`;
- ссылки отклонений, гипотез и экспериментов на новые реестры;
- новые экономические реестры пусты, если не было отдельного подтверждённого решения;
- source/target fingerprints, transformation report и read-back доказательства.

## Инструменты

~~~bash
python3 scripts/migrate_template_v0_3_to_v0_4.py --help
python3 scripts/build_template_v0_4.py --summary
~~~

Скрипт миграции принимает полный inventory значений, а не скриншот и не вычисляемый лист. Сначала строится план. Batch разрешён только после закрытия всех `REQUIRES_INPUT`.

## 1. Зафиксировать источник

1. Проверить, что source имеет точную schema v0.3: 32 листа, заголовки, version selectors и отсутствие необъявленного structural drift.
2. Сохранить `spreadsheet_id`, revision, numeric sheet IDs, named range IDs, counts, authoring values и source fingerprint.
3. Создать backup либо отдельную целевую копию. Никогда не направлять структурный batch на source ID.

Если источник не является точной v0.3, остановиться. Сначала нужен отдельный drift assessment или предыдущая миграция.

## 2. Построить read-only план

План классифицирует строки:

- `preserve` — перенос без смыслового изменения;
- `resolve-indicator` — legacy-`Элементы модели.element_type = показатель`;
- `resolve-requirement` — legacy-`element_type = норматив`;
- `preserve-sla` — `SLA` остаётся элементом модели;
- `regenerate` — formulas, named ranges, checks, snapshot и dashboard;
- `new-empty` — экономика и условия назначений без подтверждённого источника.

Отсутствовавший в source элемент не создаётся и не объявляется потерей миграции. Сначала доказать его наличие в v0.3.

## 3. Разрешить legacy-показатель

Для каждой строки по одному вопросу установить:

1. управленческий вопрос и решение;
2. измеряемую характеристику;
3. одну единицу наблюдения и её stable ID;
4. правило результата единицы и агрегации;
5. единицу измерения и временной смысл;
6. требуемые факты, покрытие и производственную систему; ответственность наследуется от её владельца;
7. для финансового показателя — валюту, основание признания, границу состава и сверку.

Провести identity test. При сохранённой идентичности старый `element_id` становится `indicator_id`. Система-источник, locator-контракт, требуемый факт, покрытие, актуальность, роль и период образуют отдельную привязку. Если они неизвестны, показатель не считается принятым и миграция остаётся `REQUIRES_INPUT`.

Legacy-`owner_position_id` показателя не переносится в отдельное поле: v0.4 выводит ответственность через `system_id → владелец производственной системы`. Migration report сохраняет прежний owner ID как свидетельство преобразования, чтобы его можно было проверить, но не создаёт параллельного владельца показателя.

## 4. Разрешить legacy-норматив

Для каждой строки по одному вопросу установить:

1. принятый `indicator_id`;
2. область и stable ID элемента;
3. оператор `равно`, `не менее`, `не более`, `диапазон` либо `формула`;
4. ровно одну совместимую форму значения;
5. начало и при необходимости конец периода;
6. является ли это новой редакцией существующего требования.

Старый `element_id` становится `requirement_id` только при сохранённой идентичности требования. SLA не преобразуется автоматически. Свободный текст, похожий на норматив, не является разрешением.

## 5. Не выдумывать экономику

Миграция добавляет пустые листы `Экономические правила` и `Условия назначений`. Она не превращает автоматически:

- цену позиции контракта в наблюдение выручки;
- поле исполнителя в условие назначения;
- название расхода в три классификационные оси;
- сумму выплаты в стоимость позиции;
- пустое значение в ноль.

Экономика появляется отдельным mutation package после полного интервью и подтверждения владельца.

## 6. Показать и подтвердить пакет

Пакет содержит source/target IDs, fingerprints, counts, каждое преобразование stable ID, before/after, вопросы и ответы, ссылки отклонений/гипотез/экспериментов, пустые новые реестры, preconditions, recovery и ожидаемый target fingerprint. Любая правка меняет `package_hash`.

Простое «да» разрешает запись только после показа всего неизменённого пакета. ИИ не подтверждает.

## 7. Построить и применить batch

1. Builder v0.4 создаёт 37 листов, named ranges, validations, checks, snapshot и dashboard.
2. Sparse restore возвращает только существующие значения и разрешённые преобразования; вычисляемые формулы не затираются статическим текстом.
3. Batch применяется к target copy одной migration transaction.
4. При timeout сначала искать transaction и сверять частичную запись; не запускать второй независимый перенос.

## 8. Перечитать и принять

Проверить:

- 37 листов и точные заголовки;
- сохранность всех незатронутых строк и stable IDs;
- отсутствие legacy-типов `показатель` и `норматив` в `Элементы модели`;
- сохранность `SLA`;
- ссылки `norm_requirement_id` и `primary_metric_id`;
- отсутствие выдуманных экономических строк;
- formulas, selectors, named ranges, checks, snapshot и dashboard;
- source/target counts, fingerprints и transformation report.

Статус `готово` допустим только после read-back и reconciliation. До этого результат называется `черновик миграции`.

## Откат

Source v0.3 остаётся неизменной reader-only точкой отката. Ошибка target исправляется повторной сборкой отдельной копии либо новой подтверждённой редакцией; исходную книгу и её историю не переписывают.
