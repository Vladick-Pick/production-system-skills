# Миграция рабочей книги v0.2 → v0.3

Этот runbook является частью `maintain-production-system`. Он меняет версию табличного продукта, а не смысл производственной системы. Исходная v0.2 не редактируется; rollback — продолжить работу в ней.

## Результат

Отдельная копия v0.3, в которой:

- сохранены все существующие авторские, версионные и исторические значения и stable IDs;
- ровно 32 листа в порядке schema v0.3;
- `Отклонения`, `Гипотезы` и `Эксперименты` добавлены пустыми;
- `Инструкция`, `Схема шаблона`, `Срез модели`, `Проверки`, `Реестр процессов` и `Рабочая панель` пересобраны builder v0.3;
- source/target reconciliation доказывает отсутствие потерь;
- исходная v0.2 остаётся неизменной точкой отката.

Миграция не принимает новую версию бизнес-модели и не вводит её в действие.

## 1. Read-only inventory

До вопросов и записи зафиксировать:

- `spreadsheet_id`, revision и доступ;
- `schema_version=0.2` и builder fingerprint;
- точный порядок 29 листов;
- counts и значения всех авторских, identity, governance и derived-registry строк;
- named ranges, formulas, validations и protections;
- текущие `model_id`, `working_version_id`, `current_version_id`;
- backup locator.

Не считать вычисляемые листы вторым набором авторских данных. Не объявлять отсутствующий в источнике элемент потерей миграции.

Нормализованный inventory для детерминированной проверки имеет поля:

~~~json
{
  "schema_version": "0.2",
  "spreadsheet_id": "...",
  "build_fingerprint": "...",
  "sheet_order": ["Инструкция", "...", "Диаграммы"],
  "sheets": {"Система": [], "...": []}
}
~~~

`sheets` содержит каждый лист v0.2 ровно один раз. В production inventory строки должны сохранять точные `userEnteredValue`, а не только отформатированный вид.

## 2. Stop-gates

Остановить перенос до нового решения, если:

- schema version, состав или порядок листов не соответствует v0.2;
- builder fingerprint неизвестен;
- источник изменился после inventory;
- один stable ID имеет конфликтующие редакции;
- отсутствует backup или нельзя доказать неизменность исходной книги;
- копирование или read-back не позволяет проверить точные значения.

Drift сначала описывается; его нельзя молча нормализовать под ожидаемую схему.

## 3. План

Выполнить:

~~~bash
python3 scripts/migrate_template_v0_2_to_v0_3.py source-inventory.json --output migration-plan.json
~~~

План обязан вернуть:

- source fingerprint;
- список сохраняемых листов и counts;
- exact target order из 32 листов;
- три пустых новых реестра;
- шесть служебных листов для пересборки;
- одинаковые source/target fingerprints сохраняемых значений;
- детерминированный `migration_id` и plan fingerprint.

План не является разрешением на внешнюю запись.

## 4. Показать пакет и получить подтверждение

Показать человеку:

- точную исходную и целевую книги;
- что копируется без смысловых изменений;
- какие служебные поверхности пересобираются;
- что новые реестры будут пустыми;
- stop-gates, проверки и rollback;
- `migration_id`, counts и fingerprints.

Получить подтверждение неизменённого package по `INTERVIEW-CONTRACT.md`. Локальный ответ на вопрос не разрешает миграцию.

## 5. Собрать отдельную копию

1. Создать копию исходной v0.2; исходник не менять.
2. Снять повторный read-only inventory и сравнить source fingerprint.
3. Применить `template-schema-v0.2.json` + overlay `template-schema-v0.3.json` через `scripts/build_template_v0_3.py` к целевой структуре.
4. Восстановить точные пользовательские значения сохраняемых листов по исходному inventory, не восстанавливая поверх новых formulas вычисляемые ID и служебные диапазоны.
5. Оставить три новых реестра пустыми.
6. Пересобрать resolver snapshot и вычисляемые представления.
7. Не создавать прошлые отклонения, гипотезы или эксперименты по косвенным признакам.

При runtime без настоящей atomic transaction сохранять `migration_id` и checkpoint до первого batch. Timeout сначала проверять read-back, не запускать второй независимый перенос.

## 6. Reconciliation

Снять target inventory и выполнить:

~~~bash
python3 scripts/migrate_template_v0_2_to_v0_3.py source-inventory.json \
  --target target-inventory.json \
  --output migration-verification.json
~~~

Приёмка требует одновременно:

- 29→32 листа в точном порядке;
- каждый сохраняемый лист имеет те же значения и counts;
- прежние stable IDs, версии, решения и история не изменены;
- новые реестры пусты;
- служебные листы пересобраны и не содержат формульных ошибок;
- selectors показывают читаемый текст, ID открыты рядом;
- `Рабочая панель` наполняет выбранный процесс или явно показывает отсутствие данных;
- source inventory после миграции совпадает с исходным fingerprint.

Если расходится хотя бы одно существующее значение, v0.3-копия не принята.

## 7. Recovery и rollback

- timeout → read-back по `migration_id`;
- частичный target → не продолжать молча; либо завершить тот же план при неизменных preconditions, либо создать новую копию;
- source drift → отменить target и повторить inventory;
- формульный дефект → исправить schema/builder в репозитории и пересобрать новую копию;
- потеря значения → остановить приёмку; не компенсировать догадкой;
- rollback → открыть исходную неизменённую v0.2 и продолжить работу там.

Удаление неудачной копии не требуется для восстановления и выполняется только отдельным явно разрешённым действием.

## 8. Отчёт человеку

Сначала сказать простыми словами:

1. создана ли отдельная v0.3-копия;
2. какие существующие данные доказанно сохранены;
3. что добавлено новым и почему реестры пусты;
4. работает ли `Рабочая панель`;
5. какие blockers или неизвестные остались;
6. можно ли пользоваться копией и где находится rollback.

Затем привести `migration_id`, source/target fingerprints, counts, verification result и точные stop-gates.
