# Собрать производственную систему

Основной результат — одна проверенная черновая версия выбранного контура в канонической модели вместе с решением, transaction, materialized snapshot и projection readiness. Заполненная таблица без исполнимых путей и истории результатом не считается.

## Когда использовать

Использовать для:

- первичной модели нового бизнеса или внутренней производственной системы;
- существенного нового контура, которого ещё нет в модели;
- наполнения пустого шаблона из допущенных определений.

Если существующие stable IDs уже меняются, основной workflow — `maintain-production-system`. Если спорен один элемент — сначала `resolve-model-element`. Для проверки без записи — `audit-production-system`.

## Обязательные контракты

Полностью прочитать:

1. `references/LANGUAGE.md`;
2. `references/METAONTOLOGY.md`;
3. `references/INTERVIEW-CONTRACT.md`;
4. `references/TEMPLATE-CONTRACT.md`;
5. `references/TEMPLATE-SCHEMA-v0.2.json`;
6. `references/PROJECTION-CONTRACT.md`.

Не добавлять столбцы, enum, relation type или формулы. Ограничение схемы оформить отдельным предложением владельцу.

## Preconditions

Установить в state `orient`:

- точную книгу, `model_id` и schema version;
- `working_version_id` и `current_version_id`;
- режим `read-only`, `proposal` или `write`;
- имя и фамилию текущего человека;
- `performer_id` и активные назначения;
- границу моделируемого бизнеса и его внутренних систем;
- цель, слой, явные нецели и источники.

Если книга не соответствует v0.2 schema, не писать v0.2 строки «по похожим колонкам». Для v0.1 вернуть migration requirement по `templates/migrations/v0.1-to-v0.2.md`.

Нового человека зарегистрировать в `Исполнители` и связать с позицией только внутри первой подтверждённой transaction. Один человек может иметь несколько назначений. AI не подтверждает mutation.

## Интервью

### 1. Исследовать до вопросов

Прочитать разрешённый snapshot, источники и уже принятые решения. Определить, какие факты доступны, какие утверждения конфликтуют и чего действительно не хватает.

Не записывать ответы по ходу интервью. В state `resolve` задавать ровно один вопрос, затем обновлять checkpoint. Локальное «да» подтверждает только ответ на вопрос.

### 2. Задать систему от продукта назад

Установить:

- продукт и единицу производства;
- получателя и критерии приёмки;
- мотивированный отказ;
- внутреннюю систему-производителя;
- владельца результата;
- входящие внешние продукты и контрагентов;
- контракты, позиции контрактов и интерфейсы передачи;
- действия, в которых внешний компонент используется.

Не создавать внешнюю производственную систему поставщика или заказчика. Внешняя сторона — контрагент; в модели остаются компонент, условия, цена, интерфейс, приёмка и внутреннее использование.

### 3. Пройти исполнение вперёд

~~~text
триггер
→ вход/объект
→ первое ответственное действие
→ решения, передачи и исключения
→ конечный выход
→ приёмка или мотивированный отказ
~~~

Продуктовый и исполнительский пути должны встретиться. Иначе найдена деятельность без продукта или продукт без производящего пути.

### 4. Составить инвентарь кандидатов

Извлечь точные слова и source locators для:

- внутренних систем и позиций;
- продуктов и контрагентов;
- объектов, состояний и переходов;
- процессов, действий и связей действий;
- исполнителей и назначений;
- решений, условий и исключений;
- правил, данных, источников истины, ИС и автоматизаций;
- материалов;
- контрактов, позиций контрактов и интерфейсов передачи;
- показателей, нормативов и SLA.

Инвентарь не является моделью. Новый или спорный элемент провести через `resolve-model-element` и получить semantic-resolution package.

### 5. Смоделировать идентичности и жизненные циклы

Для каждого объекта установить референт, stable ID, создание, сохранение идентичности, завершение и состояния. Обязательно проверять превращения по логике `Лид / Квалифицированный лид`: новое состояние не превращать в новый объект и наоборот.

Разделять модель процесса, живой экземпляр, объект работы и CRM-запись. Один экземпляр процесса имеет один основной объект работы.

### 6. Смоделировать продукты и материалы

Продукт отдельно заказывают и принимают; конкретный результат — экземпляр. Изменение только цены/срока не создаёт новый продукт. Два отдельно принимаемых качества — два продукта.

Материал — переиспользуемый текст/URL. Конкретное сообщение является данными исполнения. Использование хранится relation row `действие → использует → материал`; отдельный лист связей материалов не создаётся.

### 7. Выделить процессы и действия

Процесс имеет stable ID, цель, trigger, вход, общий выход, один основной объект, состояния, владельца и полный граф.

Одно действие имеет одну ответственную позицию, один тип, наблюдаемый вход и один выход/изменение/решение. Разделить формулировку при нескольких независимых глаголах, смене позиции, нескольких переходах или отдельной автоматизации.

Граф обязан содержать start, все существенные условия, решения, передачи, исключения, возвраты, timer/SLA и terminal outcomes. Каждый не terminal узел имеет исходящий edge, каждый узел достижим.

### 8. Смоделировать ответственность и средства

Позиция описывает устойчивую ответственность. Исполнитель и назначение ведутся отдельно. Автоматизация и AI исполняют от имени позиции, но не заменяют её ответственность.

Информационная система — среда функций, данных и интерфейсов; процесс может проходить через несколько систем и вне них. Не писать «CRM выполняет процесс» без действия, позиции и automation mapping.

### 9. Смоделировать контракты и передачи

Один контракт может иметь несколько products и `Позиции контрактов` с отдельными price/unit/quality. Интерфейс передачи фиксирует trigger, channel, format, package, acceptance, rejection, return и fallback.

Передача завершается принятием, отказом или timeout, а не статусом отправителя. Использование компонента связывать с конкретными действиями; процессы и системы выводить по этим relations.

## Mutation package

### 10. Собрать один связный пакет

После закрытия вопросов перейти в `draft` и показать:

- границу, продукт и acceptance;
- editor/assignments и base version;
- все semantic-resolution packages;
- точные операции `применить/исключить` по 29-листовой schema;
- новые stable IDs и selectors;
- полный граф действий и состояний;
- продукты, материалы, контрагентов и contract items;
- source/status для каждой строки;
- ожидаемые `Решения` и `Изменения модели`;
- scenario results;
- projection impact/readiness;
- preconditions, recovery и остаточные конфликты.

Вычислить `package_id` и SHA-256 `package_hash`. Любая коррекция создаёт новый hash.

### 11. Получить подтверждение

Идентифицированный человек с активным назначением либо с новым performer/assignment внутри того же пакета подтверждает запись показанного package/hash. AI не подтверждает. Если пакет содержит отдельный переход версии, он должен быть назван явно; обычная первичная запись оставляет working version в `черновик`.

Подтверждение одного определения не разрешает остальные строки. После compaction без доказуемого hash запросить новое подтверждение.

### 12. Записать одной transaction

Перед commit перечитать preconditions. Затем одной идемпотентной transaction записать:

1. при необходимости `Исполнители` и `Назначения`;
2. `Решения` с confirmation и hash;
3. разреженные authoring rows рабочей версии;
4. `Изменения модели`;
5. materialized `Срез модели` и вычисляемые представления.

Порядок authoring dependencies: источники/версии → система/позиции → продукты/контрагенты → объекты/состояния → процессы → действия/edges → переходы → elements/materials → contracts/items/interfaces → model relations.

Не писать вычисляемые поля вручную. Retry сначала ищет `transaction_id`.

## Проверка

### 13. Проиграть минимум три сценария

1. normal path до принятого продукта;
2. отказ/исключение;
3. возврат, исправление, timeout или reopen.

На каждом шаге назвать объект и state before/after, position, input/evidence, output/evidence, edge и reason. «Дальше как-то» означает дефект.

### 14. Проверить запись и срез

Перечитать transaction, authoring rows, journals и resolved snapshot. Проверить schema, FK, readable selectors/open IDs, one draft, graph reachability, branch completeness, state ownership и semantic conflicts. Зелёная формула не доказывает правильный референт.

### 15. Построить проекцию

Из exact snapshot подготовить projection IR, BPMN, SVG и manifest по `PROJECTION-CONTRACT.md`. Не строить draw.io. Unknown job type, FEEL, form, binding или Modeler evidence блокирует deployment readiness, но не обязательно view readiness.

## Postconditions

- одна verified transaction и одна working draft;
- авторские строки имеют version operation и source;
- старые версии не переписаны;
- решения/изменения append-only;
- snapshot воспроизводим;
- human-readable selectors совпадают с открытыми IDs;
- scenarios завершены без устных дополнений;
- BPMN/SVG имеют один fingerprint либо blockers явно записаны.

## Recovery

- timeout → read-back по `transaction_id`;
- partial write → дописать ту же transaction только при сохранённых preconditions, иначе компенсирующая редакция;
- concurrent editor → пересобрать package/hash и получить новое подтверждение;
- compaction → восстановить checkpoint, active question, package и write state;
- schema drift → остановить запись;
- semantic unknown → оставить `кандидат/конфликт/неизвестно`, не выдумывать.

## Результат

Вернуть verified draft version: boundary/product, unresolved elements, transaction ID, decision/change IDs, snapshot checks, scenario evidence, projection build/readiness, recovery state и handoff в `maintain-production-system` для дальнейших изменений или ввода.

## Критические нарушения

- ответы пишутся до полного подтверждения;
- внешний контрагент моделируется выдуманной системой;
- product/material/data смешаны;
- принимаемая версия переписана;
- selector или ID скрыт/неоднозначен;
- transaction частична, но объявлена завершённой;
- draw.io создаётся как новая каноническая проекция;
- XML parse выдаётся за Camunda Modeler validation.
