# Изменить производственную систему

Основной результат — одна проверенная транзакция изменения существующей модели: решение, разреженные редакции, append-only история, разрешённый срез, влияние, миграция живых экземпляров и согласованная проекция. Перезаписанная строка без воспроизводимой истории результатом не считается.

## Когда использовать

Использовать, когда существуют stable IDs и требуется:

- исправить определение или классификацию;
- изменить продукт, процесс, действие, состояние, правило, ответственность, материал, контракт или интерфейс;
- принять целевое изменение и подготовить ввод в действие;
- закрыть версию или выпустить корректирующую версию;
- пересобрать производные представления после принятого изменения.

Для новой системы использовать `model-production-system`. Если спорен смысл элемента — сначала `resolve-model-element`. Для диагноза без записи — `audit-production-system`.

## Обязательные контракты

Полностью прочитать:

1. `references/LANGUAGE.md`;
2. `references/METAONTOLOGY.md`;
3. `references/INTERVIEW-CONTRACT.md`;
4. `references/TEMPLATE-CONTRACT.md`;
5. `references/TEMPLATE-SCHEMA-v0.2.json`;
6. `references/PROJECTION-CONTRACT.md`.

Не добавлять столбцы, enum, relation type или формулы. Ограничение схемы оформить отдельным предложением владельцу.

## Preconditions

В state `orient` установить:

- точную книгу, `model_id`, schema version и допустимый режим записи;
- `working_version_id`, `base_version_id` и текущую действующую версию;
- имя и фамилию текущего человека, `performer_id` и активные назначения;
- точный запрос на изменение, источник, основание и ожидаемый эффект;
- затрагиваемую границу и явные нецели;
- незавершённую transaction, конфликт редакторов или stale snapshot.

Если человека нет в `Исполнители`, спросить позицию. Регистрацию и назначения записать только в первой подтверждённой transaction. Один человек может занимать несколько позиций. AI не подтверждает изменение.

Если книга v0.1, не писать строки v0.2 «по похожим колонкам»: вернуть migration requirement по локальному `references/MIGRATION-v0.1-to-v0.2.md`.

Для детерминированной работы использовать поставляемые вместе со скиллом инструменты: `scripts/versioning/resolve.py` собирает sparse snapshot, `scripts/bpmn/generate.py` и `scripts/bpmn/validate.py` пересобирают и проверяют BPMN/SVG, `scripts/build_template_v0_2.py` воспроизводит физический контракт новой книги при отдельно разрешённом выпуске. Не предполагать наличие исходного репозитория рядом с установленным скиллом.

## Исследование изменения

### 1. Зафиксировать исходное состояние

Прочитать разрешённый snapshot базовой версии, исходные authoring rows, решения, изменения, источники, связанные процессы и последнюю projection build. Нельзя определять влияние по одному листу.

Если вход содержит semantic-resolution package, проверить его `package_id`, hash, referent, decision и freshness. Если пакета нет или изменение меняет смысл, провести затронутые элементы через `resolve-model-element`.

### 2. Уточнять по одному вопросу

Следовать `INTERVIEW-CONTRACT.md`: один вопрос, затем checkpoint. Не записывать ответы по ходу интервью. Локальное «да» подтверждает только текущий ответ, а не mutation.

Для каждого изменения выяснить:

- куда оно встраивается и какие stable IDs затрагивает;
- что было истинно до изменения и что должно стать истинно;
- причина: ошибка описания, новое решение, изменение живого исполнения или новая цель;
- зависимости, ожидаемый эффект и критерий проверки;
- какие активные экземпляры уже идут по старому правилу;
- изменились ли граница, идентичность, продукт, критерий приёмки или только условие поставки.

### 3. Классифицировать изменение

- `редакционное` — смысл и исполнение не меняются;
- `исправление` — модель неверно описывала уже существующую практику;
- `целевое` — принято новое правило, ещё не введённое в действие;
- `кинетическое` — живое исполнение уже изменилось;
- `структурное` — меняются границы, identity, продукт, graph или ownership.

Класс не выдаёт разрешение на запись. Подтверждает полный пакет идентифицированный человек, работающий с моделью; назначение фиксирует атрибуцию и не является permission/RBAC.

### 4. Повторно разрешить семантику

Проверить семь тестов `METAONTOLOGY.md`. Особое внимание:

- объект против состояния: `Лид` и `Квалифицированный лид` — один объект, если identity сохраняется, и два объекта только при самостоятельной identity/lifecycle/use;
- продукт против версии продукта: отдельно заказываемые и принимаемые качества — разные products; цена, срок и условие поставки меняют contract item, а не identity продукта;
- материал против данных исполнения: шаблон сообщения — материал, конкретное отправленное сообщение — данные экземпляра;
- информационная система — среда функций, данных и интерфейсов, а не автоматический исполнитель всего процесса;
- внешний поставщик или заказчик — контрагент, пока граница модели явно не расширена.

## Карта влияния

### 5. Найти прямое и производное влияние

Построить карту минимум по:

- products, contract items, materials и counterparties;
- objects, states, transitions и work instances;
- processes, actions, edges, decisions, positions и assignments;
- information systems, automation bindings, sources и controls;
- interfaces, acceptance/rejection, prices, units, SLA и fallback;
- resolved snapshot, checks, registry, dashboard, BPMN, SVG и manifest.

Использование внешнего компонента фиксировать на конкретных действиях. Производные процессы и системы вычислять по relations, а не дублировать вручную.

### 6. Определить миграцию живых экземпляров

Для каждого затронутого активного экземпляра выбрать и обосновать:

- завершить по старой действующей версии;
- мигрировать на новую с указанной точки и преобразованием данных/состояния;
- остановить и перезапустить;
- исключить из автоматического перехода и передать на ручное решение.

Без правила миграции версия может быть `принято`, но не `действует`, если изменение влияет на живое исполнение.

## Версия и mutation package

### 7. Создать разреженную редакцию

Не копировать всю предыдущую версию. В working version записывать только:

- новые элементы — `применить`;
- изменённые элементы с теми же stable IDs — новая редакция `применить`;
- исключённые элементы — `исключить`.

Неизменённые элементы наследуются resolver через цепочку predecessor. Принятые и действующие версии неизменяемы. Для одной модели допускается одна рабочая версия `черновик`.

### 8. Собрать один полный пакет

В state `draft` показать:

- editor/assignments, base и target version;
- reason/class/source и ожидаемый эффект;
- все semantic-resolution packages;
- точные операции по 29-листовой schema;
- before/after для каждого stable ID;
- прямое и производное влияние;
- миграцию активных экземпляров;
- новые строки `Решения` и `Изменения модели`;
- version transition, если он есть;
- scenario и projection checks;
- preconditions, recovery и остаточные неизвестные.

Вычислить `package_id` и SHA-256 `package_hash`. Любая правка, новая строка или смена transition требует нового hash.

### 9. Получить человеческое подтверждение

Идентифицированный человек, работающий с моделью, подтверждает запись именно показанного package/hash. Существующие либо новые performer/assignment входят в пакет для атрибуции, а не как permission/RBAC. AI не подтверждает. Подтверждение одного определения не разрешает зависимые изменения. После compaction без доказуемого hash запросить новое подтверждение.

### 10. Записать одной идемпотентной transaction

Перед commit перечитать preconditions и убедиться, что base snapshot не изменился. Затем одной transaction записать:

1. при необходимости `Исполнители` и `Назначения`;
2. `Решения` с confirmation и hash;
3. разреженные authoring rows;
4. `Изменения модели` для каждого затронутого stable ID;
5. materialized `Срез модели` и вычисляемые представления.

Retry сначала ищет `transaction_id`. Частичную запись нельзя объявлять завершённой.

## Жизненный цикл версии

Допустимы только четыре состояния:

- `черновик` — редактируется и не является принятой истиной;
- `принято` — решение утверждено, но ещё не заявлено как живое исполнение;
- `действует` — версия введена в работу с датой и миграционным решением;
- `закрыто` — версия больше не применяется или её разработка прекращена; обязательны решение, дата, преемник либо его отсутствие и судьба активных экземпляров, но отдельный классификатор причины пока не вводится.

Допустимы только переходы:

1. `черновик → принято`;
2. `черновик → закрыто`;
3. `принято → действует`;
4. `принято → закрыто`;
5. `действует → закрыто`.

Принятие и ввод в действие — всегда разные решения и две записи перехода. Обычно это два mutation packages и два подтверждения. Для доказанной чисто описательной коррекции уже действующей практики один заранее показанный пакет и одно подтверждение могут содержать оба строго упорядоченных решения; критерии исключения заданы в `METAONTOLOGY.md`. Закрытие требует решения, даты, successor либо явного отсутствия преемника и правила для активных экземпляров; обоснование при необходимости хранится в решении. Rollback не открывает старую версию: создаётся новая корректирующая версия, которая наследует нужное состояние модели.

## Проверка и проекция

### 11. Разрешить snapshot и сценарии

Resolver проходит predecessor chain, применяет первую найденную редакцию или exclusion и отвергает cycle, missing predecessor, duplicate draft и ambiguous revision. Сохранить snapshot fingerprint.

Повторно проиграть normal, reject/exception и return/timeout/reopen. Проверить state before/after, responsible position, input/output evidence, branch и terminal outcome. Для structural/kinetic change сравнить сценарии до и после.

### 12. Пересобрать производные артефакты

Из exact snapshot построить один projection IR, затем BPMN, SVG и manifest с одним fingerprint. Не строить draw.io. Unknown connector, FEEL, form, binding или отсутствие точного Camunda Modeler evidence блокирует deployment readiness, но может оставить view readiness.

Перечитать transaction, journals, snapshot и build. Проверить schema, FK, readable selectors/open IDs, one draft, graph reachability, migration и совпадение hashes.

## Recovery

- timeout → read-back по `transaction_id`;
- partial write → продолжать ту же transaction только при сохранённых preconditions, иначе компенсирующая редакция;
- concurrent editor → пересобрать impact/package/hash и подтвердить заново;
- stale snapshot → отменить commit и разрешить новую base version;
- compaction → восстановить checkpoint, active question, package и write state;
- schema drift → остановить запись;
- ошибочное принятое изменение → новая корректирующая версия, не переписывание истории.

## Результат

Вернуть transaction ID, decision/change IDs, version transition, changed stable IDs, impact and migration, snapshot fingerprint, scenario evidence, projection build/readiness, recovery state и unresolved blockers.

## Критические нарушения

- строка переписана без новой revision и истории;
- скопирована вся предыдущая версия вместо sparse delta;
- ответы записаны до подтверждения полного package/hash;
- подтверждение приписано AI или неизвестному человеку;
- `принято` и `действует` смешаны;
- rollback переписывает старую версию;
- живые экземпляры оставлены без решения;
- selector не читаем или technical ID скрыт;
- draw.io создаётся как новая каноническая проекция;
- XML parse выдан за Camunda Modeler validation.
